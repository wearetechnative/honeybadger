## Context

See `proposal.md` - Why. The requirement is in `specs/`.

The operator's process, as it stands and as the auditor accepts it:

```
badgersbay ──download──▶ TARI-00023-2026-09-17-wouter.toorren.tar.gz
                                   │
               ./RUNME.sh check-output <that archive>
                                   │
                    honeybadger-…-xlsx.md ──▶ operator fills the sheet
                                   │
             OneDrive folder TARI-00023-2026-09-17-wouter.toorren/
               ← output folder + reports generated by check-output
```

badgersbay's `evidence_download_name()` produces the archive name from the register: asset ID, the
date the submission was received, and `owner_to_slug()` of the owner. The folder name and `N` are
that name. This change makes the report say so.

## Goals / Non-Goals

**Goals**
- `A` and `N` filled when the archive name carries them, and only then.
- Identical output for every other input.

**Non-Goals**
- Looking the asset up in badgersbay. The name already carries it, and a lookup would make the
  submission token a way to ask the server about assets.
- Filling `C`. The name carries a slug (`wouter.toorren`), the register column a full name.
- Renaming the report files. They are named for the directory inside the archive.

## Decisions

### Recognising the convention

A name is a badgersbay download when it matches:

```
^(TARI-[0-9]{5})-([0-9]{4}-[0-9]{2}-[0-9]{2})(-[a-z0-9.]+)?\.tar(\.gz)?$
```

- The asset ID has the register's form. Column `M` is `=MID(N2,12,10)`: it reads the date from the
  twelfth character, which is only right when the asset ID is ten characters long. A name with any
  other shape would give `M` a wrong date, so it is not taken.
- The date must parse as a calendar date.
- The owner slug is optional: badgersbay omits it when the register names no owner.
- Anything else - `honeybadger-lobos-wtoorren-25-09-2026.tar.gz`, an unmatched submission's
  `PF3NCBYR-2026-09-17.tar.gz`, a browser's `... (1).tar.gz` - is not a download name, and `A` and
  `N` stay with the operator.

`N` is the name without `.tar.gz` or `.tar`: the folder the evidence goes into, as the rows already
in the sheet have it.

### Where the name comes from

`check-output` knows the path it was given before it extracts it. It passes the base name to
`generate_xlsx_asset_row_report()` as an optional second argument. The audit calls the generator
without one, since a local audit's archive never has a badgersbay name, and `check-output` on a
directory passes none either.

### The date is the submission date

The date in the name is when badgersbay received the archive, not when the scan ran. That is
accepted as the audit date: the ISO process files evidence under the name badgersbay gives it, and
`M` should agree with the folder it points to.

## Risks / Trade-offs

**A renamed download is not recognised.** An operator who renames the file loses the filled
columns and gets today's report. That is the safe direction: a name the report cannot trust is not
put in a cell.

**The report trusts badgersbay's name.** If the register had the wrong asset for a serial, the
name would carry it and so would the report. The report names the archive as its source, so the
provenance is visible, and the register is where identity is corrected.
